# git-strata 0.2.3 — status bar, daemon activity and kickstart upgrades

## No store migration

The store schema stays at v7 and no migration runs on the first 0.2.3 daemon
start. 0.2.2 and 0.2.3 open each other's stores, so there is no backup to make
for the schema and no downgrade procedure beyond reinstalling 0.2.2. No config
edits are required.

## Upgrade with kickstart, not daemon stop/start

- Upgrade the CLI, daemon and hook callers together. After
  `brew upgrade git-strata`, restart the existing LaunchAgent in place with
  `launchctl kickstart -k gui/$(id -u)/com.gwd.git-stratad`, check
  `git-strata daemon status`, then run `npx skills update git-strata -g`.
  Never start a second daemon with `brew services`.
- The formula caveats and the README now say the same. They no longer suggest
  `git-strata daemon stop && git-strata daemon start` after an upgrade.
- Before `brew uninstall git-strata`, run `git-strata daemon stop`, and only
  after it succeeds remove `~/Library/LaunchAgents/com.gwd.git-stratad.plist`
  and uninstall. If stop fails or times out, do not continue.

## `daemon status`: activity, Busy, volume, scan and identity

A 0.2.3 daemon lists the new feature `daemon_status.activity` in `features`.
When it does, `daemon_status` and `git-strata daemon status` carry these
add-only fields (absent from a down or older daemon). They are read from
memory and never slow the reply:

- `version`, `pid`, `started`: which daemon answered and since when (RFC 3339).
- `activity`: long work in flight, oldest first (`[]` when idle), each with
  `kind` (`move`, `deps_rollout`, `base_build`, `session_create`,
  `deps_install`, `publish`, `push`), `origin` (`request` or `background`),
  `repo`, `session`, `started`, `elapsed_ms`, `step_elapsed_ms`, plus fields of
  its kind (a move's `cause` and `phase`, a rollout's `sessions` and `done`).
- `busy`: `{total, recent, truncated}`, the `Busy` replies requests got because
  a lock or a size scan was slow to let go (`reason` `lock_wait` or
  `du_cancel_timeout`). `recent` keeps the last 50 of the past 10 minutes.
- `volume`: `{free, size, as_of}` in bytes for the volume holding the data
  root, sampled every 10 s; null until a sample succeeds or after one fails.
  On APFS `free` leaves out purgeable space, so it reads lower than Finder.
- `scan`: `{running, active, queued, done, full, unresolved_n}`.
- `holders[]` items gain `origin` and `elapsed_ms`. Their `session` is the
  session the holder works on when it names one (a catch-up move names the
  session it moves), else the request's own session.

Clients should check `features` for `daemon_status.activity` before relying on
any of these fields.

## LongHold: 30 s for requests, 30 min for background work

A held lock raises a `LongHold` alert after 30 s for a request, and after
30 min for background work (such as the 60 s catch-up loop's moves) or for a
holder whose move, rollout, base build or session creation is in flight
(measured per step). The alert names the holder's `method`, `repo`, `since`,
`origin` and `session`. Routine background catch-up no longer shows as a red
LongHold after 30 s.

## `du`: active and unresolved size-scan units

`git-strata du` reports `data.scan.active` (units being measured now) and
`data.scan.unresolved` (one `{unit, error, at}` per unit whose last measurement
failed, dropped once that unit is measured or confirmed gone; a directory that
cannot be read keeps the entries of the units under it). `scan.failed` still
counts every failed measurement. `git-strata help du` lists both fields.

## Desktop app: status bar

- A new in-window status bar shows up to three chips and `+N`, ordered by
  severity: critical volume space and errors, Waiting for you, repositories
  needing an agent for conflicts, degraded states (Busy replies, abnormal
  holds, long waits, failed auto-rebases, config not applied), normal
  background work, then size-scan counts. Each chip opens the matching section
  of the daemon modal, the waiting list or the session.
- The right side keeps the savings upper bound, session count and theme
  control, and adds free space when the daemon reports it.
- The daemon modal and Daemon screen show classified warnings, storage bounds
  that say when they are inexact, scan counts, and withhold the cumulative
  savings figure when the daemon gives no accuracy flag. "Not responding" now
  needs repeated health timeouts, and stale reads say how long ago they were
  updated.
- With a 0.2.2 daemon the bar still works: it classifies LongHold alerts
  itself (a request hold, or a background hold past 30 min) and leaves out
  free space, activity and Busy details.
- The conflict card's title and subtitle no longer repeat the same sentence,
  and an unreadable trash reads "no trash entries reported" instead of
  claiming the trash is empty.

## Desktop app: tray

The menu-bar tray keeps its states, shapes and colours. It no longer raises
notices for background LongHold alerts, and the Syncing tooltip names the
catch-up work's repository and elapsed time.

## Validation note

The full workspace test run hit one known timing flake under load,
`auto_close_audit::two_sessions_hooks_append_concurrently`; it passed on its
own and with its whole test binary run serially. The version bump exposed a
desktop test that compared a 0.2.2 daemon fixture with the app's version; the
test now reads the fixture as the app's own version (no product change), and
`bun run check` passes.
