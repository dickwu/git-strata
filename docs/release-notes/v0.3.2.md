# git-strata 0.3.2 — `new`/`add` no longer wait behind the repo lock

`git-strata new` and `add` no longer block behind a busy repo write lock before they create anything, and a refusal that happens before anything was written is retried by the CLI. **Upgrade the CLI and the daemon together:** the retry needs both, an older daemon never marks a refusal replay-safe, and an older CLI against this daemon gets a certified refusal once, without retrying.

## No store migration

The store schema stays at v7 and `DOWNGRADE_FLOOR` stays 0.3.0. 0.3.1 and 0.3.2 open each other's stores, so there is no backup to make for the schema. No config edits are required.

## Upgrade the CLI and daemon together

This is an exception to the usual rule that a new CLI works against an older daemon. A new CLI against an older daemon keeps the old blocking `new`/`add` and retries nothing. An older CLI against a new daemon sees `Busy lock_wait` once, with no retry. The daemon advertises the change as the feature `new.fetch_skip`. Install both from the same release, as with every earlier upgrade (see [v0.2.3](v0.2.3.md#upgrade-with-kickstart-not-daemon-stopstart) for the kickstart procedure).

## `new` and `add` without the repo lock

The full description is in [new-lock.md](new-lock.md); in short:

- `new` and `add` read main's tip, the publish-chain top and the anchor from a snapshot the daemon refreshes each time a repo lock is released. A due fetch that cannot take the lock is skipped: the session is built on main as last fetched, and `warnings` gets `{kind: "FetchSkipped", repo, holder, holder_session, last_fetch_at}` (also printed on stderr). Pinning, shadow refs and unpinning on `rm` no longer take the repo lock.
- Once the session exists, `new`'s follow-up (anchor) steps can still wait behind the current holder before the reply.
- When a lock or session-queue wait expires before anything was created, `new`/`add` refuse with `Busy lock_wait` and `detail.retry_safe: true`. The CLI sends such a refusal again, backing off from 1 s to 10 s, for `--timeout SECS` (else `GIT_STRATA_TIMEOUT`, else 600 s; `0` is unlimited). The budget bounds only the retries, never one call. Every `lock_wait` refusal now names its holder (`holder`, `holder_session`, `holder_origin`, `holder_since`, `held_ms`); once the budget is spent the last refusal also carries `detail.retries`, `detail.waited_ms` and `detail.fix`.
- A `new` that an agent's own tool timeout kills may still have created the session: check `git-strata ls` for the ticket before running it again.

## Lock-free old-tree check

The check of whether a tree left behind by a move or sync still has writers now runs on its own worker and walks without the repo lock. It takes the session queue only briefly, yields to foreground requests, and holds the repo lock only for the final comparison. `rm`, `restore`, `sync`, `deps approve`, publish's rebase, `resolve` and automatic closing stop a check of their session and wait until it has left. The desktop status bar shows the check as "Checking old tree · <repo>".

## Dependencies

Cargo and bun dependencies are refreshed within Rust 1.100 (clap 4.6.10, toml 1.2.3, zip 9.8.2, zbus 6.5.0, hyper 1.13.0, wry 0.57.4, @tanstack/react-query 5.108.4, antd 6.7.2, oxlint 1.95.0 and other patch and minor updates). The Turso engine stays pinned at `=0.9.0-pre.5`, with its internal crates held at pre.5 rather than moving to pre.6, so the metadata store engine is the same as in 0.3.1.

## Validation note

In the full workspace run, two tests failed under load and passed when rerun alone (three runs of `strata-deps --test changes`, two of `strata-daemon --test confirm_flow`): `confirm_flow` `pin_relax_needed_for_confirm_to_apply` ("another git-stratad is running" on the test daemon lock, a known load flake) and `strata-deps` `lockfile_and_manifest_parser_fixtures` (`changes_busy`, the package summary was not ready yet). Everything else in the done bar passed.
